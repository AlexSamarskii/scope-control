# Настройка и эксплуатация

[← Scope Control](../README.md)

Команды выполняются из корня проекта с настроенными переменными окружения.
Здесь собраны инструкции для существующей установки: обновления, почта,
анализ запросов, резервные копии и восстановление.

## Обновление установки

В существующей среде сохраните прежние DATABASE_URL, SECRET_KEY и SALT_KEY.
После переноса из app/ все команды выполняются из корня репозитория.
Перезапустите web/worker из нового расположения. Если STATIC_ROOT, MEDIA_ROOT
или PRIVATE_MEDIA_ROOT заданы абсолютными путями, проверьте их соответствие
новому расположению каталогов.
Остановите web/worker, выполните из корня проекта, затем запустите их снова:

```sh
uv run --no-env-file --group test python manage.py migrate --noinput
uv run --no-env-file --group test python manage.py collectstatic --noinput
```

Миграция `0018_invitation_delivery` добавляет состояние отправки приглашений.
Старые приглашения получают «Результат прежней отправки неизвестен» и не
рассылаются автоматически. Повторная инициализация владельца или БД не нужна.
Миграция `0019_project_workspace` добавляет обратимый архив и признак учебного
проекта. Существующие проекты остаются активными и обычными; учебные записи
создаются только по вашему явному действию в интерфейсе.

Формы показывают оценку только для допработ, а основание ответа — при принятии
или отказе. Переключение сохраняет ввод до ухода со страницы. Черновик можно
скопировать кнопкой; это не отправка сообщения. Новая версия объёма начинается
с прежних условий: отредактируйте их, проверьте различия и отдельно подтвердите.
Подтверждённые версии и старые решения остаются неизменными.

Фото профиля и логотип компании доступны через авторизованные маршруты
приложения: свой профиль и компания с действующим доступом. Не публикуйте
MEDIA_ROOT целиком через reverse proxy: в проверенном профиле это не требуется.
Загрузка ограничена 5 МБ / 20 миллионами пикселей. Изображения нормализуются;
при отсутствии файла показывается стандартный аватар. Частные хранилища
документов и backup не подключаются к этим маршрутам.

## Почта и приглашения

Владелец приглашает сотрудника через «Участники компании». При регистрации
адрес зафиксирован приглашением; до нативного подтверждения email вступление
невозможно. Недействительные, истёкшие и отозванные приглашения доступа не дают.
Роль «менеджер» использует существующую роль `admin`, без второй системы прав.

Доставка требует настроенного SMTP и Celery worker. EMAIL_URL и DEFAULT_FROM_EMAIL
задаются в окружении; внешняя SMTP-доставка пока не проверена. Не используйте
console mail backend для реальных адресов: письма содержат секретные ссылки.
Второй процесс с теми же переменными:

```sh
uv run --no-env-file --group test celery -A project.celeryapp:app worker \
  --pool solo --concurrency 1 --queues default --loglevel WARNING
```

При недоступной очереди приглашение сохраняется со статусом ожидания.
Владелец/менеджер может повторить отправку в списке участников; права на
назначаемую роль сохраняются. Между повторами есть пауза 60 секунд, для
незавершённой попытки — 120 секунд. При неизвестном результате прежнее письмо
могло быть принято обработчиком: явный повтор может дать второе письмо с той
же ссылкой. Отзыв/истечение не позволяют начать новую попытку.

После восстановления очереди оператор может повторно поставить до 100
ожидающих приглашений:

```sh
uv run --no-env-file --group test python manage.py reconcile_scope_invitations
```

Команда не повторяет автоматически завершённую, ошибочную или неопределённую
почтовую отправку. Отдельное расписание этой команды не устанавливалось.
«Почтовая обработка завершена» означает успешное завершение настроенного
почтового обработчика, а не доказательство SMTP-доставки или прочтения письма.
Участник (`member`) и наблюдатель (`viewer`) имеют чтение; менеджер (`admin`)
ведёт проекты, решения и приглашения в пределах своей роли; владелец (`owner`)
также управляет владельцами и запросами удаления.

SMTP-доставка вне процесса не проверялась. Автоматические проверки используют
локальную память для почты и проходят настоящий allauth confirmation flow.
Solo worker — режим разработки на macOS, не production-рекомендация.

## Работа с запросами и решениями

Ручной сценарий работает и с отключённой моделью. Для него не нужны ключ Yandex,
worker или beat; расходы на вызовы не возникают. Старый проверенный анализ можно
связать с решением только для того же запроса. Он остаётся предложением.

1. В запросе клиента нажмите «Зафиксировать решение». Выберите собственную
   категорию, введите описание и основание; явно подтвердите сохранение.
   Категория и подтверждение не выбраны заранее. Одна карточка на запрос.
2. Для возможного изменения задайте сумму, валюту RUB/USD/EUR и влияние на срок.
   Пустая сумма означает неизвестную оценку; 0 — вашу бесплатную оценку.
   Приложение не рассчитывает смету и не конвертирует валюты. Для двух других
   категорий денежные поля и влияние на срок остаются пустыми.
3. Скопируйте текст черновика из карточки или скачайте его. Передайте клиенту
   самостоятельно; затем через «Передача / ответ клиента» отметьте передачу.
   Пока оценка неполна, передача и принятие не записываются.
4. Запишите принятие или отказ: кто ответил, когда и на основании какого текста.
   Время вводится в часовом поясе компании. Описание источника/ссылка необязательны
   и не загружаются сервером. Подтверждение изначально выключено.
5. Для исправления решения, оценки или основания создайте новую редакцию.
   История сохраняется, прежнее принятие не переносится; нужен новый цикл
   передачи и ответа. Внесённая в объём карточка требует нового запроса.
6. Принятое изменение можно внести в объём отдельным действием. Подготовьте
   полный новый текст вручную, откройте предпросмотр и отдельно подтвердите
   неизменяемую версию. Изменение текста требует повторного предпросмотра;
   его подтверждение действует 30 минут. Если после исходного запроса объём
   уже обновился, применение остановится: создайте запрос по актуальной версии
   и проверьте условия заново. Автоматического слияния нет.
7. В проекте откройте «Текущие редакции карточек» или скачайте CSV-реестр.
   Он содержит текущие решения и последнее основание ответа для каждой текущей
   редакции; полная история находится в карточке. Выгрузка ограничена 1000
   карточками: при превышении сервер откажет без частичного файла. Пользовательские
   текстовые ячейки начинаются апострофом для защиты от формул таблиц.

Действующие участники компании читают карточки/историю/выгрузки, owner/admin
сохраняют решения и действия. CSV и текст создаются по запросу без публичной
ссылки/сохранённого файла, с `Cache-Control: private, no-store`. Повтор той же
отправки не создаёт новую карточку, событие или версию; устаревшая форма требует
повторной проверки. Старые запросы, анализы и решения сохраняют исходную версию.

Запись принятия менеджером не означает проверенную подпись, доставку, продажу
или оплату. Приложение не отправляет сообщения и не выставляет счета.
Инструкции резервного копирования, восстановления и удаления приведены ниже.
Клиентский портал отсутствует. Production-развёртывание и качество внешнего
анализа ещё не проверены.

## Анализ запросов

### Тестовый адаптер

Откройте проект → «Новый запрос клиента», выберите подтверждённую версию,
введите запрос (до 20 000 символов) и описание источника (до 2 000).
Сохранение не запускает обработку. Запрос неизменяем; исправление — новый запрос.
Ссылки источника хранятся текстом, сервер их не загружает.

Анализ по умолчанию отключён. Для локального синтетического сценария задайте
**до запуска web, worker и beat** одинаковое значение:

```sh
export SCOPE_ANALYSIS_BACKEND=fixture
```

После сохранения запроса нажмите «Запустить тестовый анализ» и «Обновить статус».
Fixture возвращает «Недостаточно данных» и явную пометку, что модель не подключена.
Это проверка обработки/валидации, а не ИИ-классификация реального запроса.
Результаты сохраняют исходную версию, даже когда в проекте уже есть новая.
Только владелец/менеджер запускает обработку; member/viewer читают.

Кроме worker из предыдущего раздела, для повторов и восстановления нужен beat
с теми же переменными окружения (отдельный процесс):

```sh
uv run --no-env-file --group test celery -A project.celeryapp:app beat \
  --schedule "${TMPDIR:-/tmp}/scope-control-beat-state" --loglevel WARNING
```

Включено только согласованное расписание reconciler каждые 30 секунд.
Старые фоновые demo/billing/cleanup jobs не возвращены. При недоступной очереди
запрос/запуск остаётся в PostgreSQL. После восстановления Redis/worker можно
не ждать beat и выполнить:

```sh
uv run --no-env-file --group test python manage.py reconcile_scope_analysis
```

Проход обрабатывает до 100 ожидающих/прерванных запусков. Lease попытки — 120 s;
просроченная попытка закрывается, поздний worker не переписывает результат.
Максимум три попытки, задержки временных повторов 10/60 s. Невалидный ответ
не повторяется автоматически. Статус не обещает выполнения, пока процессы остановлены.

Начальные квоты компании: 10 новых запусков за скользящий час, 50 попыток за
UTC-день, суммарно по пользователям и проектам. При необходимости задайте
положительные SCOPE_ANALYSIS_RUNS_PER_HOUR и SCOPE_ANALYSIS_ATTEMPTS_PER_DAY.
Ошибки и прерванные попытки учитываются; повтор того же ключа — без новой квоты.
Fixture не делает внешних вызовов. Для Yandex предусмотрен денежный учёт
из следующего раздела; кроме имени backend нужны профиль, согласие и ключ worker.

### Yandex AI Studio

Подключение к YandexGPT проверено реальным запросом: успешный вызов подтвердил
владелец проекта. Локальные автоматические тесты проверяют протокол и обработку
ошибок. Успешный вызов API сам по себе не измеряет качество интерпретации запросов;
проверяйте вывод модели по исходным условиям. Для настройки нужны аккаунт,
API-ключ сервисного аккаунта и ID каталога в российской инсталляции.

1. Создайте обычный Yandex Cloud аккаунт с рублёвой оплатой Model Gallery и каталогом
   в российской инсталляции. Подписка AI Studio Go — другой способ доступа;
   эти инструкции рассчитаны на API-ключ сервисного аккаунта, не подписку.
2. Создайте отдельный сервисный аккаунт с правом вызова текстовых моделей
   в выбранном каталоге и API-ключ с областью `yc.ai.languageModels.execute`.
   Инструкции провайдера: [создание ключа](https://aistudio.yandex.ru/ru/docs/ai-studio/operations/get-api-key)
   и [аутентификация](https://aistudio.yandex.ru/ru/docs/ai-studio/api-ref/authentication).
   Нужна секретная часть ключа, а не его идентификатор. Секретную часть ключа храните у оператора.
3. Проверьте [действующий тариф](https://aistudio.yandex.ru/ru/docs/ai-studio/pricing)
   и условия обработки. Профиль приложения: явный `yandexgpt-5.1`,
   0.8 ₽/1000 входящих и исходящих токенов с НДС, проверено 2026-11-06.
   Дата подтверждения действительна 7 дней; при изменении тарифа профиль в коде
   надо актуализировать до продолжения вызовов. Header отключения логирования
   для улучшения сервиса не означает полного отсутствия хранения у провайдера.
4. В web/worker/beat задайте одинаковые публичные параметры ниже и базовые
   DATABASE_URL/REDIS_URL/SECRET_KEY/SALT_KEY из раздела локального запуска.
   На первом этапе разрешены только синтетические материалы.

```sh
export SCOPE_ANALYSIS_BACKEND=yandex
export SCOPE_YANDEX_FOLDER_ID='YOUR_RU_FOLDER_ID'
export SCOPE_YANDEX_PROCESSING_APPROVED=True
export SCOPE_YANDEX_PRICE_CONFIRMED_ON=2026-11-06
```

В примере указана дата фактической проверки тарифа в этой реализации;
не продлевайте её без проверки условий. Упомянутый folder ID замените своим.
`SCOPE_YANDEX_PROCESSING_APPROVED` — подтверждение оператора для выбранного
RU аккаунта и синтетического сценария, не автоматический аудит географии.

Только в терминале worker прочитайте ключ скрытым вводом (zsh):

```sh
read -rs 'SCOPE_YANDEX_API_KEY?API-ключ Yandex (ввод скрыт): '
export SCOPE_YANDEX_API_KEY
```

Ключ не нужен web и CLI проверки. Он читается только дочерним HTTP-процессом
worker, не попадает в settings/БД/argv/логи и не загружается из файлов.
Настройки передаются через окружение процессов.

Перезапустите web, worker и beat с новой конфигурацией; команды запуска уже
приведены выше. После `migrate` доступны два пути проверки:

- В интерфейсе создайте **синтетический** проект/объём и запрос. На странице
  запроса явно подтвердите отправку четырёх текстов в Yandex AI Studio, затем
  нажмите «Запустить анализ моделью». Результат остаётся предложением.
- Для воспроизводимой проверки создайте отдельный **пустой** проект. Возьмите
  team/project UUID из его URL и UUID действующего владельца/менеджера.
  Команда ниже сама подтверждает фиксированный синтетический объём и создаёт
  синтетический запрос; существующие несинтетические материалы она не отправляет.

```sh
uv run --no-env-file --group test python manage.py shell -c \
  'from usermodel.models import User; print(User.objects.get(email="owner@example.com").pk)'

uv run --no-env-file --group test python manage.py run_model_smoke \
  --team-id YOUR_TEAM_UUID --project-id YOUR_EMPTY_PROJECT_UUID --user-id YOUR_USER_UUID
```

Замените email на адрес своего локального пользователя. Smoke ждёт настоящий
worker до 600 секунд. Успех — `status: pass` и сохранённые modelVersion/usage/
расход. Без worker, ключа, доступа или валидного ответа команда возвращает
ошибку `blocked`; это не повод подменять ответ fixture. При остановке CLI run
остаётся в БД. Вывод не содержит исходников/ответа/ключа.

Общий wallet — **100 ₽ суммарно для всех компаний**, без автоматического
пополнения по дню/месяцу или смене профиля. Перед попыткой резервируется
27.8528 ₽ по верхним пределам модели, а не по грубой оценке длины текста.
Успешный достоверный usage уточняет расход и освобождает остаток. Если платный
вызов уже отправлен, но исход неизвестен, полный резерв сохраняется; следующая
попытка требует новый резерв. Три неопределённые попытки занимают 83.5584 ₽,
после чего четвёртая не помещается в оставшийся лимит. Это расход/резерв
инфраструктуры анализа, а не цена изменения для клиента и не подтверждение оплаты.

Приложение не усекает большой объём: tokenizer получает полный CompletionRequest;
при превышении 30720 входных токенов генерация не запускается. Цитаты должны
однозначно совпасть с источниками. Refusal, усечённый или невалидный ответ
не выдаётся за анализ; реальные семантические ошибки ещё требуют оценки на
40 независимых отложенных примерах перед приёмкой качества анализа.

## Резервные копии и удаление

Функции проверены локально на новых синтетических БД PostgreSQL 17.7. Отдельный
production-носитель, сохранность ключа, расписание и восстановление при потере
всего сервера ещё не проверены. Локальные цели RPO 24 часа / RTO 60 минут —
эксплуатационные ориентиры, не SLA. Не загружайте реальные документы до проверки
мест хранения, разрешений клиента и обработки данных.

Все команды ниже запускает оператор из корня проекта с настроенным окружением Django;
префикс — `uv run --no-env-file --group test python manage.py`. Ключ
`SCOPE_BACKUP_KEY` поступает **только из окружения оператора**: Fernet key,
сохранённый оператором отдельно от архивов. Не передавайте его в argv, чат,
Django settings или файлы проекта. Потеря ключа делает копии невосстановимыми;
режима plaintext нет. Web/worker ключ backup не нужен.

До первого запроса удаления настройте абсолютные существующие owned каталоги
0700 и создайте первую копию/пустой независимый inventory:

- `SCOPE_BACKUP_ROOT`: приватный каталог только архивов; файлы 0600.
- `SCOPE_DELETION_INVENTORY_PATH`: файл в **другом** приватном каталоге, вне root
  архивов; реестр должен переживать потерю исходной БД и быть актуальным.
- `SCOPE_PG_CLIENT_MODE=native`, `SCOPE_PG_DUMP_BINARY` и
  `SCOPE_PG_RESTORE_BINARY`: явно выбранные PostgreSQL **17** clients.
  Наличие host 18.3 не проходит эту проверку. Текущий native профиль принимает
  только локальный socket/loopback; удалённый production TLS-профиль не принят.

```sh
uv run --no-env-file --group test python manage.py create_scope_backup
uv run --no-env-file --group test python manage.py prune_scope_backups --check-age
```

Копия — compressed custom pg_dump, до 64 MiB plaintext в памяти, затем
аутентифицированный Fernet archive до 96 MiB. Нет SQL/plaintext-файла, HTTP backup,
загрузки произвольного dump или копирования `.env`/медиа/Redis/ролей кластера.
UUID копии и безопасная metadata выводятся командой. Неизвестные предупреждения,
размеры, таймауты и версия tools приводят к отказу без успешного archive.

Для **локального синтетического испытания** разрешён `container_synthetic`:
`SCOPE_PG_CONTAINER=scope-control-s1-postgres-1`, `SCOPE_DOCKER_CONFIG` — отдельный
пустой owned каталог 0700, `SCOPE_DOCKER_HOST` — socket собственного Colima.
Пароль PG передаётся child environment по имени, не в аргументах docker.
Этот профиль не разрешает Docker socket production runner и не заменяет
отдельный носитель копий. Не используйте пользовательский Docker config.

Владелец компании открывает проект → «Запросить удаление проекта», вводит точное
название → предпросмотр → отдельно отмечает подтверждение. Подпись предпросмотра
связана с владельцем, компанией, проектом, названием и последней версией;
срок 10 минут. После commit новые URL/задания/CSV/admin недоступны. Статус операции
сохраняет только служебные UUID/даты и честно показывает ожидание оператора.
Manager/admin/member не могут запросить удаление. Отмены запроса удаления нет.

Физический purge выполняется только оператором по UUID операции. Остановите
**все свои** web/worker/beat и HTTP children, проверьте завершение процессов,
запишите aware UTC timestamp и выдержите не менее 90 секунд. Флаги — заявление
оператора, а не автоматическое доказательство остановки всех серверов. Если
остановку многосерверной установки доказать нельзя, purge не выполняйте.
Сначала dry-run, затем только для явно разрешённого проекта.
`RECEIPT_UUID` замените на UUID операции удаления, `UTC_TIMESTAMP` — на
зафиксированное время остановки процессов в ISO8601 с часовым поясом UTC:

```sh
uv run --no-env-file --group test python manage.py purge_scope_projects RECEIPT_UUID
uv run --no-env-file --group test python manage.py purge_scope_projects RECEIPT_UUID --execute --maintenance --processes-stopped --quiescent-since UTC_TIMESTAMP
```

Реестр удалений шифруется и fsync до SQL purge. Если запись inventory удалась,
а SQL transaction откатилась, намерение остаётся в независимом реестре и проект
остаётся pending. После устранения причины повторите тот же UUID; не заменяйте
реестр пустым. При его потере или sequence>0 без файла операция блокируется.
Обычные ORM-запреты удаления истории сохранены. Другие компании, аккаунты и
volumes не удаляются. Known расходы и полный dispatched-unknown резерв остаются
в ledger; доказанно неотправленный резерв освобождается до нуля. Общий лимит
100 ₽ не сбрасывается. Архив квот сохраняет исходный timestamp, без новой квоты
после удаления. Уже скачанные файлы и отправленное провайдеру отозвать невозможно.

Восстановление допускается только в **заранее созданную пустую** отдельную БД
`scope_restore_<32 hex UUID>`. Оператор передаёт её URL через окружение
`SCOPE_RESTORE_DATABASE_URL`; credentials не передаются аргументами команды.
Исходная БД не перезаписывается. `BACKUP_UUID` — UUID выбранной копии, который
выводится при её создании. Сначала проверка без записи, затем restore:

```sh
uv run --no-env-file --group test python manage.py restore_scope_backup BACKUP_UUID
uv run --no-env-file --group test python manage.py restore_scope_backup BACKUP_UUID --execute
uv run --no-env-file --group test python manage.py verify_scope_recovery
```

Нужны правильный ключ, authenticated копия моложе 7 суток и **текущий** независимый
реестр той же установки, sequence не ниже копии, refreshed не старше 24 часов.
Команда не получает реестр из старого DB snapshot. Refresh делается только из
полного canonical inventory командой backup либо `prune_scope_backups --execute`.
Старые копии не возвращают удалённые проекты: внешние tombstones и pending markers
копии удаляются из target; приложение отвечает 503 даже до marker по имени БД.
Wallet suspended, старые queued/running jobs завершены, модель/claim/dispatch/
reconcile запрещены. Target использует отдельную пустую broker namespace;
не запускайте на нём mail/worker/beat/cleanup и не восстанавливайте Redis.
Failed target остаётся отдельным и заблокированным. Нет `--clean`, `--create`,
перезаписи live или команды promotion/снятия карантина этого этапа.

Сроки хранения: backup действителен 7 суток, daily prune даёт физическую границу
до 8 суток **только при работающем расписании**; минимальный deletion inventory —
30 суток и до исчезновения всех более старых backup-файлов; quota events — 48 часов
от исходного времени; financial ledger — на весь срок общего денежного лимита.
Corrupt/unknown/symlink/hardlink файлы не удаляются массово. Чистятся только
проверенные owned expired archives и собственные ciphertext orphan parts старше
24 часов в `.pending`. Уборка по умолчанию dry-run:

```sh
uv run --no-env-file --group test python manage.py prune_scope_backups
uv run --no-env-file --group test python manage.py prune_scope_backups --execute
uv run --no-env-file --group test python manage.py prune_scope_backups --check-age
```

`--check-age` возвращает nonzero при последней копии старше 24 часов или уборке,
требующей внимания. Оператор отдельно устанавливает daily backup/prune и контроль
nonzero; команды не устанавливают расписание и не настраивают независимое хранение копий и ключей.
Ограничения локальной проверки перечислены выше; отдельное production-хранилище
и восстановление после потери сервера не проверены.

## Интерфейс и переводы

Создание и переключение компаний, названия ролей, уведомления о приглашениях
и изменении роли, вход, восстановление доступа и штатные настройки двухфакторной
защиты доступны на русском. Технические идентификаторы часовых поясов (например,
`Europe/Moscow`) сохраняются без перевода.

Для локальных сообщений Django используется каталог
`mainapp/locale/ru/LC_MESSAGES/django.po`; готовый `django.mo` поставляется
вместе с исходниками. После изменения `.po` разработчик пересобирает каталог:

```sh
msgfmt --check --check-format mainapp/locale/ru/LC_MESSAGES/django.po \
  -o mainapp/locale/ru/LC_MESSAGES/django.mo
```

После обновления переводов перезапустите web и worker: Django кеширует каталог.
Сама локализация не меняет БД и не требует новой миграции.

Стили собираются Tailwind из `static/mainapp/input.css`, шаблонов приложения
и локальных шаблонов `speedpycom`. Для разработки:

```sh
npm run tailwind:watch
```

Для обновления установленной версии:

```sh
npm run tailwind:build
.venv/bin/python manage.py collectstatic --noinput
```

После этого перезапустите web и обновите страницу без кеша. Шрифты Onest и Inter
поставляются локально; для отображения интерфейса внешний сервис шрифтов не нужен.

## Проверки и отчёты

Тесты запускаются командами из [README](../README.md#проверки).
Нужен PostgreSQL с правом CREATEDB: тестовая БД создаётся отдельно.
Проверки конкурентного доступа требуют PostgreSQL; skipped на другом backend
не подтверждает их прохождение. Проверенный профиль — macOS; две проверки
backup/lifecycle используют `/private/tmp`.

JUnit XML записывается в локальный игнорируемый путь
`.agent/artifacts/test_report.xml`; существование внутренних отчётов для запуска
не требуется. Тесты используют синтетические данные. Локальные результаты
не подтверждают настройку SMTP, внешней модели или production-хранилища.

## Хранение данных

Фото профиля и логотип компании выдаются через маршруты с проверкой доступа.
Не публикуйте MEDIA_ROOT целиком через reverse proxy. Загрузка ограничена 5 МБ
и 20 миллионами пикселей; изображения нормализуются. При отсутствии файла
показывается стандартный аватар. Документы и резервные копии через эти маршруты
не выдаются.

Текст поиска маскируется в журналах Django. В access logs своего reverse proxy
также исключите query string, чтобы поисковые запросы не попадали в журналы.
Перед использованием реальных клиентских материалов проверьте условия хранения,
разрешения на обработку и, при подключении модели, условия провайдера.
